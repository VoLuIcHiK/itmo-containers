# ЛАБОРАТОРНАЯ 
## 1) Ответ на вопрос: важен ли порядок выполнения этих манифестов? Почему?

Да, порядок выполнения этих манифестов важен, и вот почему:

ConfigMap должен быть создан первым, так как он содержит настройки среды (например, POSTGRES_DB, POSTGRES_USER, POSTGRES_PASSWORD), которые будут использоваться в поде, описанном в Deployment. В Deployment эта информация передаётся через envFrom, которая ссылается на ConfigMap. Если ConfigMap не будет создан заранее, Deployment не сможет найти нужные настройки, и контейнеры не запустятся.

Service обычно создаётся после ConfigMap, но до Deployment. Service создаёт сеть, через которую можно обращаться к базе данных, что особенно важно для подключения других компонентов или взаимодействия внутри кластера. В данном случае это не критично для самого запуска подов Deployment, но желательно создавать сервис до, чтобы обеспечить доступность сети сразу после развертывания подов.

Deployment создаётся последним, так как он ссылается на ConfigMap для настройки среды и предполагает, что, если ему требуется доступ извне, сеть уже настроена через Service.

Таким образом, корректный порядок выполнения манифестов:

1) ConfigMap
2) Service
3) Deployment

Если нарушить этот порядок, могут возникнуть ошибки: Deployment не сможет получить настройки из ConfigMap или может не быть доступен через сервис сразу после запуска.

2) Вопрос: что (и почему) произойдет, если отскейлить количество реплик postgres-deployment в 0, 
затем обратно в 1, после чего попробовать снова зайти на Nextcloud? 

Ответ: Когда уменьшается количество реплик Postgres до 0, это фактически останавливает все экземпляры БД в кластере. В этот момент Nextсloud теряет соединение с БД, поскольку она больше не доступна. Когда количество реплик Postgres возвращается обратно к 1, БД снова запускается, но NextCloud все равно не может подключиться к ней. Это происходит из-за того, что NextCloud не смог установить соединение с БД (так как под был отключен) и больше не пытался подключиться автоматически.
